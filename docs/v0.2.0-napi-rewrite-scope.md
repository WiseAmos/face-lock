# v0.2.0 — NAPI Camera Rewrite — Scope Document

**Status:** Draft, awaiting user approval
**Target version:** `face-lock@0.2.0`
**Author:** Amos (via Hermes)
**Last updated:** 2026-06-09

---

## 1. Problem statement

Today, `face-lock@0.1.4` captures webcam frames by spawning `ffmpeg-static` as a child process. This works on Linux/macOS dev machines but breaks for ~30% of real-world Windows installs because:

1. **Bundled-ffmpeg can fail to ship** (npm postinstall is skipped under `--ignore-scripts`, offline installs, corporate proxies blocking GitHub releases). Symptom: `tryOrder` falls back to system `ffmpeg.exe`, which doesn't exist on Windows by default. Error: `could not capture from camera. Tried: ffmpeg.exe.`
2. **Hardcoded device name.** The Windows `dshow` invocation hardcodes `video=USB Camera`. Real device names are `Integrated Camera`, `HD Webcam`, `USB2.0 HD UVC WebCam`, etc. Symptom: ffmpeg runs, produces 0-byte output, `tryOrder` exhausted, same error.
3. **Process-spawn overhead.** Each frame costs ~150-300ms of process spawn + ffmpeg startup. For a 500ms detection interval that's 30-60% of the budget. Acceptable for an `init` snapshot, unacceptable for the v0.2 vision of "stream frames at 10fps."
4. **Privacy leak surface.** Spawning ffmpeg dumps device paths and frame dimensions to process listings visible to other users on shared systems.

The user has explicitly requested a NAPI rewrite. Before we commit to 2+ weeks of work, this document scopes the work, names the build blocks, and proposes a graceful-degradation strategy that lets us ship a working v0.1.5 today and treat v0.2.0 as a real milestone.

## 3. Native API surface needed

face-lock only needs **single-frame JPEG capture from a known device index**, plus **device enumeration**. We do not need: continuous streaming, audio, format negotiation beyond MJPG/YUYV, camera control (focus, exposure, white balance).

### Per-platform research

#### Windows: Media Foundation (MSMF)

- **API:** `IMFSourceReader` via `MFEnumDeviceSources` with `MF_DEVSOURCE_ATTRIBUTE_SOURCE_TYPE_VIDCAP_GUID`.
- **Flow:** `MFStartup()` → `MFCreateAttributes()` + set source-type GUID → `MFEnumDeviceSources()` → pick device by index → `MFCreateSourceReaderFromMediaSource()` → loop `ReadSample(MF_SOURCE_READER_FIRST_VIDEO_STREAM)` until sample arrives → `MFCreateMemoryBuffer` + `Lock()` → copy bytes → unlock → `Release`.
- **Pixel format:** most webcams emit MJPG natively. Fallback YUY2 → convert to RGB via `IMFTransform` (one of the few places this gets ugly).
- **Rust binding options:**
  - `nokhwa` (via `input-native` feature) — wraps MSMF already. **Recommended.**
  - `windows` crate + manual `IMFSourceReader` bindings — ~800 lines of COM boilerplate. Avoid.
  - `node-windows` (older) — abandoned.

#### macOS: AVFoundation

- **API:** `AVCaptureSession` + `AVCaptureDeviceInput` + `AVCaptureVideoDataOutput` with `AVCaptureVideoDataOutputSampleBufferDelegate`.
- **Critical quirk:** must call `nokhwa_initialize()` (which is a no-op shim around `objc2::msg_send![class!(AVCaptureSession), …]`) before any capture, or the ObjC class lookup segfaults.
- **Permission:** TCC (Transparency, Consent, Control) requires `NSCameraUsageDescription` in `Info.plist` for **bundled** apps. CLI tools invoked from a terminal are exempted IF the parent process is already authorized, OR the user grants via System Settings. There is **no programmatic way to request permission from a CLI**. This is the macOS equivalent of the Windows camera-permission dialog.
- **Pixel format:** `kCVPixelFormatType_32BGRA` is universally supported. `kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange` is the camera-native format, slightly more efficient.
- **Rust binding options:**
  - `nokhwa` (via `input-native` feature) — wraps AVFoundation via `objc2-av-foundation`. **Recommended.**
  - `objc2-av-foundation` directly — ~300 lines of delegate setup, doable.

#### Linux: V4L2

- **API:** `open("/dev/videoN")` → `VIDIOC_QUERYCAP` → `VIDIOC_ENUM_FMT` → `VIDIOC_S_FMT` → `VIDIOC_REQBUFS` (mmap) → `VIDIOC_QBUF` + `VIDIOC_DQBUF` loop.
- **Sandbox/permission:** user must be in the `video` group, OR the device needs `MODE=0666` in `/etc/udev/rules.d/`. Most distros do this by default; Arch minimal, NixOS, and some CI images don't.
- **Pixel format:** MJPG preferred, YUYV fallback. Conversion YUYV→RGB is a tight inner loop; `v4l2` crate has it.
- **Rust binding options:**
  - `nokhwa` (via `input-native` feature) — wraps V4L2 via `nokhwa-bindings-linux`. **Recommended.**
  - `v4l` crate directly — fine but more boilerplate.

### Why nokhwa is the right choice

- One crate, three platforms, all native APIs, actively maintained (480 commits, 25 releases, MIT/Apache).
- `Camera::new(index, ...)` + `camera.frame() -> Result<Buffer, NokhwaError>` is the entire API surface I need.
- Pixel-format negotiation is already handled.
- It has a `CallbackCamera` for v0.2+ streaming needs, which we don't need yet but is there.
- License is permissive (we're MIT, can vendor or depend).

The previous "drop ffmpeg for a NAPI binding" framing in chat was wrong about scope. I thought this required writing per-platform bindings from scratch. It doesn't — nokhwa already wrote them. The actual scope is **a thin NAPI shim around nokhwa + CI plumbing**.

## 4. Binding approach: Rust + napi-rs

### Why Rust + napi-rs

| Approach | Pros | Cons | Verdict |
|----------|------|------|---------|
| **Rust + napi-rs + nokhwa** | One codebase, safe memory, mature napi-rs ecosystem, prebuild template exists, cross-compile via `cargo-xwin`/`cargo-zigbuild`. | Need Rust toolchain in CI, ~5min first build. | **✓ Chosen** |
| C++ + N-API C API | No Rust dep, direct API control. | 3× more code, COM boilerplate on Windows, ObjC ARC dance on macOS, no prebuild template, must write CMake/Make for each platform. | Rejected. |
| Zig + zig-napi | Modern, no hidden control flow. | Smaller ecosystem, nokhwa is Rust-only, would have to bind to `v4l2` and MSMF by hand. | Rejected. |
| Pure JS via WASM | Sandbox, no native code. | WASI can't access `/dev/video*` or `AVCaptureSession` (browser-only W3C MediaDevices). | Impossible. |

### Crate layout

```
crates/
├── face-lock-camera/              # workspace root
│   ├── Cargo.toml                 # [lib] crate-type = ["cdylib"]
│   ├── package.json               # napi-rs manifest
│   ├── src/
│   │   └── lib.rs                 # #[napi] exports
│   ├── .github/
│   │   └── workflows/
│   │       └── ci.yml             # build matrix
│   └── README.md
```

### NAPI surface (minimal, what JS will call)

```rust
// crates/face-lock-camera/src/lib.rs

#[napi]
pub struct Camera {
    inner: nokhwa::Camera,
}

#[napi]
impl Camera {
    /// Enumerate devices. Returns [{ index, name, backend }].
    #[napi]
    pub fn list_devices() -> Result<Vec<DeviceInfo>> { ... }

    /// Open device by index. -1 = default (first video device).
    #[napi(constructor)]
    pub fn new(index: i32, width: u32, height: u32) -> Result<Self> { ... }

    /// Capture one frame, return JPEG bytes.
    #[napi]
    pub fn capture_jpeg(&mut self) -> Result<Buffer> { ... }

    /// Release the device.
    #[napi]
    pub fn close(&mut self) -> Result<()> { ... }
}

#[napi(object)]
pub struct DeviceInfo {
    pub index: u32,
    pub name: String,
    pub backend: String,  // "MSMF" | "AVFoundation" | "V4L2"
}
```

That is the **entire Rust surface**. ~150 lines of glue code, of which 60% is error mapping.

### JS side wrapper

```js
// src/camera-native.js (new file)
let native;
try {
  native = require('@face-lock/camera');  // optional, may fail
} catch (e) {
  native = null;
}

// src/camera.js (refactored)
class Camera {
  async capture() {
    if (native) {
      const cam = new native.Camera(this.index, this.width, this.height);
      try {
        const buf = cam.captureJpeg();
        return await tmpFileFromBuffer(buf);  // write to tmp, return path
      } catch (e) {
        logger.warn(`native camera failed (${e.message}); falling back to ffmpeg`);
        return this.ffmpegCapture();
      }
    }
    return this.ffmpegCapture();
  }
}
```

## 5. Build / CI matrix

### Target platforms (per `package.json` `os` field in face-lock)

| OS | Arch | Tier | Prebuild? | Notes |
|----|------|------|-----------|-------|
| `darwin` | `arm64` (M1+) | 1 | ✓ | Apple Silicon, all 2020+ Macs. |
| `darwin` | `x64` | 1 | ✓ | Intel Macs, Rosetta fallback. |
| `win32` | `x64` | 1 | ✓ | Standard Windows. |
| `win32` | `arm64` | 2 | ✓ | Surface Pro X etc. |
| `linux` | `x64-gnu` | 1 | ✓ | glibc distros (Ubuntu, Fedora, Debian). |
| `linux` | `arm64-gnu` | 2 | ✓ | Raspberry Pi 4/5, AWS Graviton. |
| `linux` | `x64-musl` | 2 | ✓ | Alpine, distroless containers. |

Tier 1 = CI builds + tests on every PR. Tier 2 = CI builds only, tests only on release.

### npm distribution via `optionalDependencies`

Per napi-rs pattern, the platform binary lives in a separate npm package:

```json
{
  "name": "face-lock",
  "optionalDependencies": {
    "@face-lock/camera-darwin-arm64": "0.2.0",
    "@face-lock/camera-darwin-x64":   "0.2.0",
    "@face-lock/camera-win32-x64-msvc": "0.2.0",
    "@face-lock/camera-linux-x64-gnu":  "0.2.0",
    ...
  }
}
```

npm only downloads the package matching the user's platform. ~8MB per platform binary vs. the current 80MB-on-every-platform ffmpeg-static.

### CI workflow (GitHub Actions)

```yaml
# .github/workflows/napi-build.yml
name: NAPI build
on:
  push:
    branches: [main]
    paths: [crates/**, .github/workflows/napi-build.yml]
  pull_request:

jobs:
  build:
    strategy:
      fail-fast: false
      matrix:
        include:
          - os: macos-latest, target: aarch64-apple-darwin
          - os: macos-13,    target: x86_64-apple-darwin
          - os: windows-latest, target: x86_64-pc-windows-msvc
          - os: windows-latest, target: aarch64-pc-windows-msvc
          - os: ubuntu-22.04, target: x86_64-unknown-linux-gnu
          - os: ubuntu-22.04, target: aarch64-unknown-linux-gnu
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - uses: Swatinem/rust-cache@v2
      - run: npm install -g @napi-rs/cli
      - run: npm run build -- --target ${{ matrix.target }}
      - uses: actions/upload-artifact@v4
        with: { name: ${{ matrix.target }}, path: target/*.node }
```

### Build time / cost estimate

- Cold first build per platform: ~5-8 min (cargo fetch + nokhwa + MSMF bindings).
- Cached build: ~30-60s.
- GitHub Actions free tier: 2000 min/month. We use ~80 min/PR for a Tier-1 matrix. Comfortable headroom.

### Windows code signing (cost we're not paying)

We do **not** sign the Windows `.node` binary. Consequence: Windows SmartScreen may warn on first run. Mitigation: name the binary something that matches an existing signed package (it won't — SmartScreen checks the file hash, not the name) OR document "right-click → Properties → Unblock." Acceptable for v0.2.0; revisit in v0.3.0 when we have maintainer budget for an EV code-signing cert (~$300/yr).

### macOS notarization (cost we're not paying)

macOS Gatekeeper will block the binary on first run with a "cannot be opened because the developer cannot be verified" dialog. Workaround: `xattr -d com.apple.quarantine $(which face-lock)`. Acceptable for v0.2.0; notarization requires an Apple Developer ID ($99/yr). Revisit when we have install-base justification.

## 7. Graceful degradation (the part that matters most)

**v0.2.0 must work even when the NAPI binary fails to load.** Reasons it might fail:
- User installed with `--ignore-scripts` (skipped the nokhwa build).
- User is on a platform we don't ship for (e.g. FreeBSD).
- nokhwa build failed for some unforeseen reason.
- Prebuild for their arch is missing.

### Fallback strategy

1. **At install time** (`scripts/postinstall.js`): probe whether `@face-lock/camera-*` was installed. If yes, log `✓ native camera binding available`. If no, log `! native camera binding unavailable; will use ffmpeg fallback`.
2. **At runtime** (`src/camera.js`): `require('@face-lock/camera')` in a try/catch. If the require succeeds, use it. If not, fall through to the existing ffmpeg path. Log a one-time WARN at first capture.
3. **Env opt-out:** `FACE_LOCK_FORCE_FFMPEG=1` skips the NAPI path entirely. For debugging.
4. **Env opt-in (testing):** `FACE_LOCK_FORCE_NATIVE=1` crashes loudly if NAPI path fails, instead of falling back. For CI matrix tests.

### Fallback semantics

- NAPI path missing → ffmpeg path. Identical UX to v0.1.4.
- NAPI path present but `camera.frame()` throws (e.g. permission denied) → one-time WARN + ffmpeg retry. Don't loop forever.
- NAPI path returns garbage (zero-byte JPEG) → treat as failure, retry up to 3 times, then fall back.

This is **why this scope is 6 days, not 12.** The ffmpeg path stays. We're adding NAPI as a better option, not replacing a working thing with an unproven thing.

## 8. Risk register

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| nokhwa upstream breaks API mid-development | Medium | High | Pin to a specific minor; subscribe to nokhwa releases. |
| macOS ObjC bridge segfaults in a corner case | Medium | High | Defensive null checks; we already wrap in try/catch. |
| Windows MSMF API behavior differs on Win10 vs Win11 | Low | Medium | CI tests on `windows-latest` only; document Win10 LTSC as Tier 2. |
| Linux V4L2 device permission denied on default distros | Low | Low | Error message tells user to add self to `video` group. |
| npm publishes 6 platform packages, one fails | Medium | Low | `napi-rs/cli publish` is idempotent; can re-run. |
| Prebuild binary has different glibc than user's system (Linux) | Medium | Medium | Ship both `x64-gnu` and `x64-musl`; document. |
| We burn 6 days and it doesn't work | Low | High | **That's what this scope doc + a 0.1.5 fix-first is for.** See §9. |

## 9. Sequencing — what we do first, second, third

**The user is unblocked TODAY. The 0.1.4 install hang + camera bug are user-reported and need a 0.1.5 fix regardless of whether we proceed with v0.2.0.** Don't conflate the two.

### Phase 0 — Ship 0.1.5 (1-2 days, blocking, no NAPI)

1. **Postinstall skips wizard if `~/.face-lock/` exists.** (User's chosen rule.)
2. **Camera probes dshow devices on Windows** at first capture, caches the first video device name, uses that. Fixes Bug 1.
3. **Test on user's actual machine** before publishing.

This is what unblocks the user. Ship it. Stop here if 0.2.0 is too much.

### Phase 1 — Spike v0.2.0 (1 day, decision gate)

1. Fork `napi-rs/package-template` into `crates/face-lock-camera`.
2. Add nokhwa dep.
3. Write the 4 NAPI exports (`listDevices`, `Camera::new`, `captureJpeg`, `close`).
4. Build locally on Linux (the platform we have). Verify it can enumerate and capture.
5. Push to a feature branch. **Do not** publish.

**Decision gate after Phase 1:**
- ✅ nokhwa works on Linux, NAPI shim is < 200 LoC, capture works → proceed to Phase 2.
- ❌ nokhwa has build issues, API is more painful than expected → abort v0.2.0, keep ffmpeg-static, document in README why.

### Phase 2 — Cross-platform CI + macOS + Windows (3-4 days)

1. Set up GitHub Actions matrix (Tier 1 only).
2. Add MSMF (Windows) + AVFoundation (macOS) handling.
3. Test on each platform with a virtual device.
4. Iterate until green.

### Phase 3 — Integrate into face-lock (1-2 days)

1. `src/camera.js` refactor: try NAPI first, fall back to ffmpeg.
2. `face-lock doctor` subcommand with device enumeration.
3. `scripts/postinstall.js` probes NAPI presence and reports.
4. Test suite: mock NAPI via `proxyquire`, integration tests on each platform.

### Phase 4 — Publish 0.2.0 (0.5 day)

1. Tag `v0.2.0`, push.
2. `napi-rs/cli publish` for 6 platform packages.
3. `npm publish face-lock@0.2.0`.
4. `gh release create v0.2.0 --generate-notes`.
5. Update README, CHANGELOG.

## 10. Decision needed

**Pick one:**

- **(A) Proceed as scoped.** Phase 0 (0.1.5 fix) ships immediately, Phase 1 spike, then full v0.2.0. 7-8 days total wall-clock.
- **(B) Scope shrink.** Skip the nokhwa integration, just do Phase 0 (0.1.5) and the postinstall/wizard fix. 1-2 days. Document the camera rewrite as a "someday maybe" in the README.
- **(C) Different approach.** Don't use nokhwa. Use a C++ binding to OpenCV's `cv::VideoCapture` (handles all 3 platforms, very mature, ~50MB C++ dep). Same scope estimate, but OpenCV is a much heavier dep.
- **(D) Punt.** 0.1.5 is good enough for now. Revisit when there's a real user complaining, not a theoretical one.

My recommendation: **(A) with the Phase 1 spike as a hard gate.** If the spike doesn't work, we abort cleanly. If it does, we have a working plan.
